## 1. 要回答的问题

1. 键盘扩展里到底能不能自己发声（不依赖 VoiceOver）？
2. 出声是否需要开启完全访问？（当前 RequestsOpenAccess = false，定位是必须保持关闭）
3. 旁白正在念焦点内容时按键，两套声音是否重叠？
4. `.sequential`（等上一条读完）模式下，`announcementDidFinish` 在扩展里到底来不来？
5. 键盘首次弹出的手感是否因合成器实例化而变慢？

## 2. 现状与为什么需要这个实验

同一个 API 在项目历史里得到过互相矛盾的结论：

| 版本 | 做法 | 真机结果 |
|---|---|---|
| 0.2.2–0.2.10 | `UIAccessibility.post(.announcement)` | 时有时无，后期完全听不到 |
| 0.2.5 | 同上，但在 UI 重建**之前**投递 | 提交信息记载「能听到」 |
| 0.2.11 | 焦点转移（`.layoutChanged`） | 能听到，但每次要等好几秒 |
| 0.2.13 起 | 又改回 announcement | 静默 |

结论：这条路依赖时序，靠推理无法收敛。因此改为「一次装机、五条通道并排比较」。

## 3. 五条通道

| 编号 | 通道 | 关键差异 |
|---|---|---|
| 1 | 应用语音，`usesApplicationAudioSession = false` | 扩展里默认 `true` 会借用应用音频会话；会话不可用时**完全没声音也不报错** |
| 2 | 应用语音，会话设为 `.playback` + `.mixWithOthers` | 验证静音开关打开时能否出声 |
| 3 | `UIAccessibility.post(.announcement)`，在 `syncUI` 之前 | 复现 0.2.5 的时机 |
| 4 | 焦点转移 | 现状基线（默认值，不改变已发布行为） |
| 5 | `.valueChanged` + 常驻候选状态元素 | 旁白对数值变化通常更敏感 |

切换方式：**三击「大小写」键**循环。切到某条通道时，该通道先朗读自己的名字。
> 听不到名字，就说明这条通道静默。这是本实验最重要的信号。

也可以在 主应用 → 设置 → 输入体验 → 按键播报 → 语音通道 里直接选。

## 4. 三条使用规则

1. **只读候选，不读键名**。键名交给 VoiceOver，否则两套声音叠在一起听不清。
   实现上：通道 1/2 传 `includeKeyName = false`。
2. **每个键都读，不去重**。已删除 `focusFirstCandidateAfterKeypress` 里
   「首候选不变就不读」的判断——静默比重复更有害。
3. **新键立即打断旧句**：`stop` → `Task.yield()` → `speak`（照调音节拍器已验证的写法），
   否则开头音节被吞。

## 5. 实现边界

- `KeySpeechComposer` / `KeySpeechSnapshot` 语义未改，只新增 `includeKeyName` 参数。
- 默认通道为 4，与已发布行为一致；不改默认值，等真值表出来再决定。
- 未触碰 `RequestsOpenAccess`。
- 未使用私有 API。

## 8. 如果通道 1、2 都完全没声

退路（本次未实现，仅记录可行性）：用 `AVSpeechSynthesizer.write` 把语音渲染成 PCM buffer，
再用 `AVAudioEngine` 播放，绕开合成器自己的播放路径。
工作量更大，但比继续调旁白可靠。

## 9. 观测方法（如何取证而不靠猜）

代码已在 `speak` / `didFinish` / `didCancel` 处加了诊断日志，带通道编号。
若「完全没声音」，先看日志判断属于哪种：

| 日志表现 | 含义 |
|---|---|
| 有 `KeySpeech channel=1 appVoice ...` 但无 `didFinish`/`didCancel` | 合成器被调用但没跑起来 |
| 有 `speak` 也有 `didFinish` | 合成器认为念完了，但音频没进扬声器（会话/路由问题） |
| 没有任何日志 | 代码路径没走到（时序或开关问题） |
