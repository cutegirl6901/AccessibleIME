# 候选朗读通道诊断实验

> 状态：**结论已出，默认口径已改；真值表仍待回填**
>
> 日期：2026-11-18 起，2026-11-24 更新
>
> 版本：0.2.17（build 20）诊断版 → 0.2.18（build 21）默认口径版
>
> 目的：一次装机排除「候选朗读完全没声音」的所有主要可能，
> 而不是每次只改一条路、只验证一条路。

## 0. 2026-11-24 结论与默认口径

本轮不改通道数量，只改**默认值**与**播报内容规则**：

| 项 | 0.2.17 | 0.2.18 |
|---|---|---|
| 默认通道 | 4 焦点转移 | **3 旁白公告（排队）** |
| 公告优先级 | `default`（打断） | **`.low`（排队）** |
| 默认投递模式 | `immediate` | **`immediate`（每次按键一条，不合并）** |
| 键名 | 键盘也念一遍 | **交给旁白，键盘只补新信息** |
| 通道 4 的闭包注入 | 只在通道号 ≠ 默认时才注入 | **无条件注入** |
| 通道数 | 5 | **6**（新增通道 6：打断式公告） |

发现的两个确定缺陷：

1. **默认通道的朗读回调从未接上。** `KeySpeechAnnouncer()` 默认构造
   焦点转移通道，而 `refreshKeySpeechSettings()` 只在「存储通道号 ≠ 默认值」
   时才调用 `installSpeechChannelCallbacks`。存储为空 → 解析结果等于默认值
   → 条件不成立 → `focusFirstCandidate` 永远是 `nil` → 每次按键都是空操作。
2. **公告用了 `default` 优先级。** 这会打断旁白正在念的键名，两条语音互相抢占，
   正是历史记录里「时有时无」的直接原因。

`UIAccessibilityPriority.low` 的官方定义是「排队，等其它语音说完再播」，
因此「旁白念键名 → 键盘念候选」是系统保证的顺序，不需要等
`announcementDidFinish`，也不需要成对回调。

## 1. 要回答的问题

1. 键盘扩展里到底能不能自己发声（不依赖 VoiceOver）？
2. 出声是否需要开启完全访问？（当前 RequestsOpenAccess = false，定位是必须保持关闭）
3. 旁白正在念焦点内容时按键，两套声音是否重叠？
4. `.sequential`（等上一条读完）模式下，`announcementDidFinish` 在扩展里到底来不来？
5. 键盘首次弹出的手感是否因合成器实例化而变慢？

## 2. 现状与为什么需要这个实验

同一个 API 在项目历史里得到过互相矛盾的结论：

| 版本 | 做法 | 真机结果 |
|---|---|---|
| 0.2.2–0.2.10 | `UIAccessibility.post(.announcement)` | 时有时无，后期完全听不到 |
| 0.2.5 | 同上，但在 UI 重建**之前**投递 | 提交信息记载「能听到」 |
| 0.2.11 | 焦点转移（`.layoutChanged`） | 能听到，但每次要等好几秒 |
| 0.2.13 起 | 又改回 announcement | 静默 |

结论：这条路依赖时序，靠推理无法收敛。因此改为「一次装机、五条通道并排比较」。

## 3. 五条通道

| 编号 | 通道 | 关键差异 |
|---|---|---|
| 1 | 应用语音，`usesApplicationAudioSession = false` | 扩展里默认 `true` 会借用应用音频会话；会话不可用时**完全没声音也不报错** |
| 2 | 应用语音，会话设为 `.playback` + `.mixWithOthers` | 验证静音开关打开时能否出声 |
| 3 | `UIAccessibility.post(.announcement)`，在 `syncUI` 之前 | 复现 0.2.5 的时机 |
| 4 | 焦点转移 | 现状基线（默认值，不改变已发布行为） |
| 5 | `.valueChanged` + 常驻候选状态元素 | 旁白对数值变化通常更敏感 |

切换方式：**三击「大小写」键**循环。切到某条通道时，该通道先朗读自己的名字。
> 听不到名字，就说明这条通道静默。这是本实验最重要的信号。

也可以在 主应用 → 设置 → 输入体验 → 按键播报 → 语音通道 里直接选。

## 4. 三条使用规则

1. **只读候选，不读键名**。键名交给 VoiceOver，否则两套声音叠在一起听不清。
   实现上：通道 1/2 传 `includeKeyName = false`。
2. **每个键都读，不去重**。已删除 `focusFirstCandidateAfterKeypress` 里
   「首候选不变就不读」的判断——静默比重复更有害。
3. **新键立即打断旧句**：`stop` → `Task.yield()` → `speak`（照调音节拍器已验证的写法），
   否则开头音节被吞。

## 5. 实现边界

- `KeySpeechComposer` / `KeySpeechSnapshot` 语义未改；`includeKeyName = false` 时
  只补「新信息」（上屏文本或首候选），不再重念键名。
- 默认通道为 3（旁白公告，`.low` 排队）；通道 4 保留为诊断备选。
- 未触碰 `RequestsOpenAccess`。
- 未使用私有 API。

## 8. 如果通道 1、2 都完全没声

退路（本次未实现，仅记录可行性）：用 `AVSpeechSynthesizer.write` 把语音渲染成 PCM buffer，
再用 `AVAudioEngine` 播放，绕开合成器自己的播放路径。
工作量更大，但比继续调旁白可靠。

## 9. 观测方法（如何取证而不靠猜）

代码已在 `speak` / `didFinish` / `didCancel` 处加了诊断日志，带通道编号。
若「完全没声音」，先看日志判断属于哪种：

| 日志表现 | 含义 |
|---|---|
| 有 `KeySpeech channel=1 appVoice ...` 但无 `didFinish`/`didCancel` | 合成器被调用但没跑起来 |
| 有 `speak` 也有 `didFinish` | 合成器认为念完了，但音频没进扬声器（会话/路由问题） |
| 没有任何日志 | 代码路径没走到（时序或开关问题） |

## 11. 结论

- **可用通道**：通道 3（旁白公告，`.low` 排队）为默认；通道 6 是同一种公告的
  打断式变体（`.default`），供快速连打时对照；通道 1/2（键盘自发声）
  在完全访问关闭时预计静默，保留为对照。
- **是否需要完全访问**：走旁白公告**不需要**。完全访问只影响「键盘自己发声」
  （`AVSpeechSynthesizer` / `playInputClick`），见 `external-keyboard-speech-research.md`。
- **下一步**：装机后先按默认口径听一遍（应听到「键名 → 候选」，不打断、不重复）；
  若听不到，再三击大小写键逐条换通道，回填第 6 节真值表。
